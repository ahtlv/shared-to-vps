# Общее и своё: откуда граница ядра и адаптера

Два переезда с одного заражённого аккаунта на одну машину: [сайт A на
MODX](case-a-modx.md) и [сайт B на WordPress](case-b-wordpress.md). Таблица
раскладывает каждую поломку на то, что повторилось бы на любой CMS, и то, что
принадлежит одной из них. Граница между [ядром и адаптером](../references/glossary.md)
проведена по этой таблице, а не наоборот.

Номера `G-1NN` лежат в [реестре ядра](../references/90-gotchas.md), `G-2NN` в
[адаптере WordPress](../adapters/wordpress/gotchas.md), `G-3NN` в
[адаптере MODX](../adapters/modx/gotchas.md).

| Что ломалось | Оказалось общим | Оказалось своим |
|---|---|---|
| Архив хостинга привёз не только сайт | Режим `0700` на докруте (G-101), лог ошибок на 1,3 ГБ в докруте (G-109), хуки деплоя прежнего подрядчика с выгрузкой базы по HTTP (G-110). Правило: всё выброшенное перечисляется списком | WordPress: установщик плагина бэкапа в докруте (G-212) |
| Коды ответа зелёные, сайт мёртв | Каждый адрес рисует главную после оборванного восстановления (G-102); статический кэш держит 200 поверх мёртвого приложения (G-113). Правило: сравнивать тела и `<title>`, делать запрос мимо кэша | MODX: путь до точки входа доходит только в `q` (G-301), закодированный `q` подменяет страницу (G-302) |
| Правка конфига не доезжает до процесса | Конфиг смонтирован файлом, `sed -i` меняет инод (G-103); у прокси суммы совпадают при отвязанном бинде (G-104). Правило: доказательство это инод | Своего нет ни у одной CMS |
| Запрет в конфиге есть, а дыра открыта | Порядок регулярных блоков (G-105), пробник без расширения `.php` (G-106). Правило: трассер живыми пробниками с доказанным отрицательным результатом | Путь загрузок принадлежит CMS: у WordPress `wp-content/uploads` (G-208), у MODX `assets/` с исполняемыми коннекторами внутри `assets/components/` (G-303) |
| Заявка теряется молча | Сообщение формы об успехе означает «валидация пройдена», а не «доставлено» (G-111). Правило: письмо во входящих получателя | WordPress: бесплатная редакция плагина форм не хранит заявки (G-201). MODX: получатели в расширении настроек со своим кэшем (G-307) |
| Страничный кэш и оформление | Своего общего правила нет, кроме G-113 | WordPress: константа кэша не попала в новый конфиг (G-206), постраничные стили без общей транзакции с кэшем (G-204) |
| Адреса и пути старой площадки | Адрес для отката и прежнее значение записей снимаются до правок (ворота Ф0) | WordPress: путь в трёх видах в базе (G-209), адрес спрятан константой (G-213), ссылка на раздел похожа на путь (G-214). MODX: медиа-источник с ведущим слэшем даёт `//assets/` (G-304), адрес сайта выводится из имени хоста и кэшируется (G-308) |
| Повтор разворачивания даёт другую базу | Правило: два прогона подряд и сравнение содержимого таблиц, а не счётчиков строк | WordPress: крон при загрузке пишет метку времени (G-207). MODX: `ON UPDATE CURRENT_TIMESTAMP` в таблицах настроек (G-310) |
| Пароль и конфиг расходятся | Секреты живут только в файле окружения с правами `600` | MODX: пароль базы в двух местах (G-305), ключ сессии в том же файле, что пароль, и бэкап без конфига не разворачивается (G-311). У WordPress конфиг и соли генерируются заново, этой грабли нет |
| Доказательство чистоты снимка | Метод обязателен и записывается числом: сверка с внешним манифестом либо диф двух снимков | WordPress: есть официальный манифест ядра (3338 файлов), но локализованная сборка сверяется со своим (G-211), а пользователи в дампе прячутся за форматом (G-210). MODX: манифеста нет, чистоту доказывал диф двух снимков |
| Правки в панели DNS ничего не меняют | Оба домена были делегированы на серверы имён прежнего хостинга (G-112). Правило: авторитетный ответ верхнего уровня, а не панель | Своего нет |
| Редиректы старой структуры | Своего общего правила нет | MODX: 177 правил, написанных руками годами, с самопереходами и повторами (G-306). У сайта B единственный редирект жил в коде сайта и переехал с ним |
| Вход администратора | Своего общего правила нет | MODX: менеджер вырезает спецсимволы из пароля (G-309) |
| Инструменты разворачивания | Своего общего правила нет | WordPress: инструмент командной строки исполняет файл как строку (G-202), правка формы через API записей ломает разметку (G-203). MODX: имя класса разрешается через импорт без учёта регистра (G-312) |
| Автоматика упирается в капчу | Доказательство доставки делает человек | WordPress: управляемый режим капчи (G-205) |

## Что из этого следует

**Ядро это путь запроса через стек и способы доказательства.** Изоляция, запреты
и их порядок, доставка конфига до процесса, делегирование, сравнение тел, запрос
мимо кэша, доставка заявки до человека. Всё это повторилось на втором переезде
буквально, хотя CMS была другая.

**Адаптер это то, как CMS читает путь и где она хранит своё.** Параметр точки
входа, каталог загрузок, место получателей заявок, форма хранения путей и
адреса в базе, собственный кэш, поля, которые пишутся сами при любом `UPDATE`.

**Почти в каждой строке общее правило одно, а его проявления разные.**
Невоспроизводимость разворачивания у обеих CMS, но причина у каждой своя;
правило «два прогона и сравнение» одно. Поэтому правило живёт в ядре, а знание
о конкретной причине в адаптере, и третья CMS принесёт новые строки в правую
колонку, а не в среднюю.

**Два переезда это не класс задач.** Таблица доказывает, что граница выведена из
фактов, но не доказывает, что она верна для третьей CMS. Это покажет только
третий переезд и число новых граблей, которое он даст.
