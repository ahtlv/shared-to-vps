# shared-to-vps

Скилл для Claude Code, ведущий переезд сайта с заражённого или развалившегося
общего хостинга на изолированный VPS. Конвейер из восьми фаз с воротами:
каждая фаза заканчивается проверяемым критерием, а не ощущением «вроде
готово».

## Для кого

Для того, кто уже решил, что сайт увозят с общего хостинга, и кому нужен не
совет «поднимите VPS», а пошаговый маршрут с доказательствами на каждом
переходе: чем доказать, что снимок чист, чем доказать, что стек изолирован,
чем доказать, что можно переключать домен.

## Какой класс задач закрывает

Сайт на общем хостинге скомпрометирован или недоступен, хостер не отвечает
или отвечает медленно, на том же аккаунте есть соседние площадки, а
существующий бэкап нужно развернуть на новом сервере так, чтобы не привезти
заражение вместе с контентом.

## Установка

```sh
git clone <адрес репозитория> ~/Work/shared-to-vps
ln -s ~/Work/shared-to-vps ~/.claude/skills/shared-to-vps
```

Если используется скилл `auto-update`, добавить блок `type=git-repo` в
`~/.claude/auto-update/registry.conf`, чтобы обновления репозитория
отслеживались вместе с остальным окружением.

## Границы применимости

**Один способ изоляции.** Контейнеры Docker Compose на одной машине, обратный
прокси перед ними, расписание через таймеры systemd. Виртуальная машина на
каждый сайт, jail, изоляция средствами панели управления не рассматриваются.
Способ выбран потому, что дважды выдержал реальные сайты и помещается в
недорогой сервер, а не потому, что он единственно верный.

**Root на целевом сервере.** Конвейер предполагает root-доступ, контейнеризацию
и обратный прокси перед стеком. Без этих трёх условий фазы, начиная со второй,
неприменимы.

Скилл не для этого:

- не для переезда между двумя общими хостингами: там нет ни root, ни
  контейнеров, и ворота второй фазы доказать нечем;
- не для управляемых платформ и оркестраторов (Kubernetes, PaaS): ядро
  собрано вокруг Docker Compose на одной машине;
- не заменяет форензику: конвейер доказывает чистоту снимка методом,
  описанным в фазе архива, но не ищет точку входа атаки и не занимается её
  атрибуцией;
- не заменяет переписку с хостером: фаза триажа фиксирует точку отката, но
  не ведёт коммуникацию с поддержкой.

Метод собран из двух переездов (MODX и WordPress). Адаптеры есть только для
этих двух CMS; для другой CMS ядро работает, а свою часть (загрузки, точки
входа, разворачивание, приёмку изнутри) придётся написать по образцу.

## Где ведётся работа

Планирование, задачи и приёмка по этому проекту ведутся в приватном трекере
автора, а не в issues этого репозитория: в них неизбежно попадают имена
заказчиков, переписка с хостингом и реквизиты конкретных площадок. Issues
этого репозитория открыты для сообщений со стороны, а не для ведения работ.

Номера внутренних задач в файлы этого репозитория не переносятся: для
читателя со стороны они всё равно битые ссылки на систему, к которой у него
нет доступа.
