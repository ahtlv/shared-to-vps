# Ф6 · Эксплуатация

**Вход:** домен переключён, сайт работает на VPS, бэкапов и сторожа ещё нет.
**Выход:** один полный цикл бэкапа и один прогон сторожа прошли на живой площадке.

## Зачем эта фаза

Набор файлов, который никто ни разу не распаковывал, бэкапом не является. Он
становится бэкапом в тот момент, когда его распаковали и импортировали, и ни
минутой раньше. Поэтому проверка стоит **до** публикации набора, а не после.

Сторож целостности решает вторую задачу: заметить изменение файлов раньше, чем его
заметит посетитель. Его эталон снимается после приёмки, иначе каждый перенесённый
файл придёт находкой и сторожа выключат на второй день.

## Порядок

Всё ниже выполняется из каталога отрендеренного стека на сервере, от root.
Настройки в трёх файлах рядом со стеком: `backup.conf`, `offsite.conf`,
`watchdog.conf`. Секретов ни в одном нет.

1. **Дописать в `backup.conf` своё от адаптера:** `exclude=` для конфига CMS с
   паролем базы и для кэша, `expect=` для точки входа CMS. Проверить
   `db_name` и `secrets_file`: без файла с паролями бэкап откажет, потому что
   проверять ему будет нечем.
2. **Собрать набор:** `scripts/backup.sh`. Скрипт сам снимает дамп одной
   транзакцией, импортирует его во временную схему, выгружает том, убирает
   исключения, архивирует, распаковывает архив в отдельный каталог и сверяет
   с исходником по составу, ищет в наборе значения живых паролей, не печатая
   их. Только после этого промежуточный каталог переименовывается в
   `ГГГГ-ММ-ДД-слаг`. Оборванный прогон видимого набора не оставляет.
3. **Проверить набор руками один раз:** `sha256sum -c SHA256SUMS` в каталоге
   набора и прочитать `RESTORE.md`. Это инструкция для человека без доступа к
   серверу, она едет в каждом наборе.
   Затем **развернуть из набора сайт**, а не только базу: отрендерить из копии
   профиля временный стек с другим слагом (`<слаг>-check`, своё имя хоста),
   поднять его, выполнить `adapter/restore.sh --archive <набор>/site-files.tar.gz
   --dump <набор>/database.sql.gz` с суммами из `SHA256SUMS` и прогнать
   `adapter/verify.sh`. Импорт дампа в `backup.sh` доказывает только базу: набор,
   из которого исключили конфиг с ключами сайта, импортируется, а сайт из него
   не встаёт. Временный стек после проверки снести вместе с томами.
4. **Сделать внешнюю копию шифрованной.** Ключевую пару age сделать **не на
   сервере**: `age-keygen -o key.txt` у себя, закрытый ключ в менеджер паролей,
   в `offsite.conf` только получатель `age1...`. Строку с закрытым ключом
   скрипт отвергает. Хранилище настроить в rclone на сервере, его имя и путь
   записать в `remote=`. Затем `scripts/backup-offsite.sh`: первая копия
   сверяется обратным чтением всегда, дальше по `--verify`.
5. **Доказать расшифровку у себя:** скачать копию, `age -d -i key.txt ... |
   tar -xf -`, `sha256sum -c`. На сервере этого не сделать, и это правильно.
6. **Дописать в `watchdog.conf` своё от адаптера:** `users_sql=` и
   `objects_sql=` (по одному числу), `uploads=`, узкие `exclude=` для кэша.
   Исключение, накрывающее каталог загрузок, сторож отвергает.
7. **Снять эталон сторожа после приёмки:** `scripts/watchdog-baseline.py`. Без
   `--force` существующий эталон не перезаписывается.
8. **Прогнать сторожа:** `scripts/watchdog-check.py`, ожидается код 0.
9. **Подсадить изменение намеренно:** файл в каталог загрузок, прогон даёт
   код 1 и называет файл; удалить, прогон снова 0. Проверка без доказанного
   отрицательного результата не гарантирует ничего.
10. **Доступ к файлам через контейнеры**, не через FTP: отдельный канал доступа
    это отдельная поверхность атаки, а история заражения на общем хостинге как
    раз про украденные реквизиты доступа.
11. **Поставить расписание.** Юниты лежат в `systemd/` стека без слага в
    имени и ставятся с ним:

    ```sh
    for f in systemd/*; do cp "$f" /etc/systemd/system/<слаг>-"$(basename "$f")"; done
    systemctl daemon-reload
    systemctl enable --now <слаг>-backup.timer <слаг>-backup-offsite.timer <слаг>-watchdog.timer
    systemctl list-timers '<слаг>-*'
    ```

    Сторож с находкой или сбоем оставляет юнит в `failed`, это видно в
    `systemctl --failed`. Уведомление при желании задаётся `notify_command=`
    в `watchdog.conf`: итог приходит ему на stdin.

## Ворота

| Что доказываем | Чем доказываем | Что записываем |
|---|---|---|
| бэкап собирается | полный цикл на живой площадке: сбор, распаковка, импорт во временную базу | размер набора, время цикла |
| бэкап восстановим | сайт развёрнут из набора на временном стеке тем же `restore.sh` адаптера, и его внутренняя приёмка зелёная | путь набора, код разворачивания, вывод приёмки |
| внешняя копия работает | копия существует и расшифровывается обратно | размер, дата, где лежит ключ (не сам ключ) |
| сторож видит правду | прогон по эталону даёт пустой список | вывод прогона |
| сторож вообще работает | подсаженное изменение найдено | что подсадили, что сторож сообщил |
| расписание живо | состояние таймеров и время следующего запуска | вывод по каждому таймеру |

**Не считается прохождением:** «таймер включён»; «набор создался»; «скрипт бэкапа
отработал без ошибок»; импорт дампа без разворачивания сайта (набор, из которого
исключили конфиг с ключами сайта, импортируется, а сайт из него не встаёт);
сторож, который ни разу ничего не находил.

**Секреты не пишутся никуда:** ни в репозиторий, ни в отчёт о самопроверке, ни в
журнал. Место для паролей одно: файл окружения с правами `600` на сервере. Отчёт
этой фазы читают люди, которым пароль базы не нужен.

## Чего не делать

- Не публиковать набор бэкапа до распаковки и импорта.
- Не хранить ключ шифрования рядом с внешней копией.
- Не снимать эталон сторожа до приёмки.
- Не открывать FTP ради удобства.
- Не писать пароли в отчёты и журналы.
- Не считать фазу законченной без прогона сторожа на подсаженном изменении.
