# Восстановление {{DOMAIN}} из набора бэкапа

Этот файл лежит в каждом наборе под именем `RESTORE.md`. Он написан для
человека, у которого на руках только набор: без доступа к серверу, без
скилла и без памяти о том, как всё было устроено.

## Что в наборе

Каталог `ГГГГ-ММ-ДД-{{SLUG}}`:

| Файл | Что это |
|---|---|
| `site-files.tar.gz` | докрут сайта целиком, распаковывается прямо в `public_html` |
| `database.sql.gz` | обычный SQL-дамп MariaDB/MySQL, без `CREATE DATABASE`: импортируется в схему с любым именем |
| `SHA256SUMS` | контрольные суммы трёх файлов |
| `RESTORE.md` | эта инструкция |

Намеренно **нет**: конфига CMS с паролем базы, файлов `.env`, журналов
ошибок, кэша. Реквизиты в переносимом наборе это утечка, которая ждёт
своего часа. Конфиг создаётся заново на новой площадке (шаг 4).

Каждый набор до публикации прошёл две проверки: архив распакован и совпал с
исходником по составу, дамп импортирован во временную схему. Набор без
`SHA256SUMS` набором не является: это оборванный прогон.

## Где взять набор

- **Сервер доступен:** `/var/backups/{{SLUG}}/`, по набору на день, самый
  новый последний по дате в имени.
- **Сервера нет:** внешняя копия, раздел ниже.

## Если доступа к этому серверу больше нет

Сервер удалён, заблокирован, взломан, хостинг-провайдер не отвечает. Для
этого случая внешняя копия и существует. Понадобятся две вещи, и ни одна из
них на сервере не хранилась:

1. **Доступ к внешнему хранилищу.** Реквизиты хранилища на сервере были в
   конфиге rclone, и вместе с сервером они потеряны. Нужен собственный вход
   владельца в это хранилище.
2. **Закрытый ключ age** (строка `AGE-SECRET-KEY-...`). Он хранится только у
   владельца, в менеджере паролей или на бумаге. Без него копия не
   расшифровывается никем, включая вас.

Скачайте нужный файл `ГГГГ-ММ-ДД-{{SLUG}}.tar.age` из хранилища любым
способом: веб-интерфейсом, клиентом хранилища или `rclone copy`. Затем:

```sh
age -d -i key.txt ГГГГ-ММ-ДД-{{SLUG}}.tar.age | tar -xf -
cd ГГГГ-ММ-ДД-{{SLUG}}
```

`age` ставится пакетом (`apt install age`, `brew install age`) или бинарём с
github.com/FiloSottile/age. Дальше как с обычным набором.

## 1. Проверить целостность

```sh
sha256sum -c SHA256SUMS
```

Все три строки должны закончиться `OK`. Если нет, возьмите набор за
предыдущий день: ротация держит несколько.

## 2. Файлы

На обычном хостинге с панелью:

```sh
mkdir public_html
tar -xzf site-files.tar.gz -C public_html
```

и залить содержимое `public_html` в корень сайта (файловым менеджером
панели, SFTP, rsync). Права: каталоги `755`, файлы `644`, владелец тот, от
кого работает PHP на этой площадке.

## 3. База

Создайте в панели пустую базу и пользователя с новым паролем, затем:

```sh
gzip -dc database.sql.gz | mysql -h ХОСТ -u ПОЛЬЗОВАТЕЛЬ -p ИМЯ_БАЗЫ
```

Через phpMyAdmin или аналог: распаковать `database.sql.gz` и импортировать
`database.sql`. Для крупного дампа лимит загрузки панели бывает мал; тогда
импорт командой выше по SSH.

## 4. Конфиг CMS

Конфига с паролем в наборе нет. Создайте его заново с реквизитами базы из
шага 3 и **новыми** ключами и солями: старые считаются скомпрометированными
вместе с сервером. Где он лежит и как называется, зависит от CMS; адаптер
скилла описывает это в своей инструкции.

## 5. Проверить до переключения домена

Откройте сайт по адресу площадки или через подмену адреса в `hosts`, не
трогая DNS: главная, две-три внутренние страницы, вход в админку, отправка
формы. Только потом переключайте домен {{DOMAIN}}.

## Развернуть на новом VPS тем же способом

Если под рукой скилл и новый сервер с докером: отрендерить стек из профиля
площадки, поднять его, распаковать архив в том сайта через контейнер
приложения, импортировать дамп через админа базы по сокету:

```sh
gzip -dc database.sql.gz | docker exec -i -u mysql {{SLUG}}-mariadb mariadb ИМЯ_БАЗЫ
```

После этого пройти приёмку и заново снять эталон сторожа: старый описывает
старый сервер.
